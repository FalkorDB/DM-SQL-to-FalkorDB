# ADR-0001: Iceberg source access strategy for v1

## Status
Accepted (feasibility spike complete).

## Context
Before committing to an architecture for `Iceberg-to-FalkorDB`, we validated the `iceberg` crate (apache/iceberg-rust), specifically:
catalog types supported, full-scan correctness (types, deletes), incremental/snapshot-scan maturity, delete-file (merge-on-read) handling, async/tokio compatibility, and dependency footprint.

This ADR records the research and hands-on validation performed, and the resulting v1 decision.

## Research findings (apache/iceberg-rust, as of crate version 0.10.1)
- **Maturity**: the `iceberg` crate is actively maintained (Apache Software Foundation project, ~1.4k GitHub stars), used in production by Databend, RisingWave, Apache DataFusion Comet, Spice.ai, and Lakekeeper. Current release `0.10.1` (Aug 2026), MSRV-tracked, Apache-2.0 licensed (compatible with this repo's `LICENSE`).
- **Catalogs available** as separate crates: `iceberg-catalog-rest` (REST catalog), `iceberg-catalog-glue` (AWS Glue), `iceberg-catalog-hms` (Hive Metastore), `iceberg-catalog-sql` (SQL-backed, e.g. sqlite/Postgres), `iceberg-catalog-s3tables` (AWS S3 Tables), plus an in-crate `MemoryCatalog`. There is **no dedicated Hadoop/filesystem catalog crate** (the plan's original assumption of a "hadoop" catalog type was incorrect); local/filesystem-only setups should use the SQL catalog (sqlite) with a `file://` warehouse, or the Memory catalog for ephemeral tests. The project explicitly notes "not all catalog implementations are complete."
- **Storage backend**: handled by the separate `iceberg-storage-opendal` crate, which wraps [Apache OpenDAL](https://opendal.apache.org/) rather than the `object_store` crate assumed in the original plan. `OpenDalResolvingStorageFactory` auto-detects the scheme (`file://`, `s3://`, `gs://`, `azblob://`, etc.) from table/file paths and requires no per-tool custom object-store code — this *simplifies* the originally proposed `common/arrow-to-falkordb-bridge` crate's scope (it no longer needs to implement its own multi-cloud storage client builder; it can wrap `iceberg-storage-opendal`'s factory and expose the same OpenDAL-based config to the Parquet connector too, since `opendal` is a general-purpose, well-maintained Rust storage abstraction independent of Iceberg).
- **Full table scan**: `table.scan().select(...).build()?.to_arrow()` returns a `Result<ArrowRecordBatchStream>` (a `BoxStream` of `RecordBatch`). This path is stable and shipped in the current release.
- **Merge-on-read deletes**: `FileScanTask` already carries a `deletes: Vec<FileScanTaskDeleteFile>` (including `equality_ids` for equality deletes), and the standard `table.scan()` path applies them automatically when building Arrow batches. **Confirmed empirically** (see Validation below): deletes are correctly merged into full-scan results.
- **Incremental/snapshot scanning**: `IncrementalAppendScanBuilder` (`table.incremental_append_scan(...)` / `appends_between(...)` / `appends_after(...)`) exists in-progress upstream (PR apache/iceberg-rust#2337, superseded by #2997, both **open/unmerged** as of this spike) and is **not yet in a released crate version**. Even once merged, it is explicitly append-only: it walks snapshot ancestry and includes only snapshots whose `Operation == Append`, silently skipping `Replace` (compaction), `Overwrite`, and `Delete` operations, and its manifest filter explicitly excludes delete manifests (`content != ManifestContentType::Deletes`). It is **not** a changelog/CDC scan.
- **Changelog/CDC scan** (the feature that would correctly express updates and deletes between two snapshots, matching Spark's `create_changelog_view`) is tracked by an **open, unimplemented** upstream issue (apache/iceberg-rust#1636) with no committed design as of this spike.
- **Row-level delete *writing*** (`RowDeltaAction`) is also still in progress upstream (#1104) — irrelevant to this read-only connector, but another signal that delete semantics are an active, not-yet-fully-settled area of the crate.

## Validation performed
A hands-on spike was run locally (not committed; throwaway):
1. Seeded a local Iceberg table (`sales.orders`, SQL/sqlite catalog, `file://` warehouse) using `pyiceberg` 0.12.0: two `append` batches (5 rows total) followed by a row-level `delete` of `id=2`, producing 3 snapshots.
2. Read the same catalog/table from a Rust binary using `iceberg = "0.10.1"`, `iceberg-catalog-sql = "0.10.1"`, and `iceberg-storage-opendal = "0.10.1"` (with `OpenDalResolvingStorageFactory`).
3. Confirmed: catalog/table interop between `pyiceberg` and `iceberg-rust` works; `table.metadata().snapshots()` correctly lists all 3 snapshots with operation tags (`append`, `append`, `overwrite`); a full `table.scan().to_arrow()` returned exactly 4 rows (`id` 1, 3, 4, 5) across 2 batches — the deleted row (`id=2`) was correctly excluded via merge-on-read, with correct Arrow types (`Int64`, `Utf8`, `Float64`, `Timestamp(Microsecond)`) and field-id metadata.
4. The crate graph compiled cleanly on this machine (macOS, stable Rust 1.96) with no native build issues beyond the expected `sqlx` sqlite driver and OpenDAL's S3/FS service crates.

## Decision
For `Iceberg-to-FalkorDB` v1:
1. **Use the standard full `table.scan()` API** (stable, released, confirmed to correctly apply merge-on-read deletes) as the read path for every run.
2. **Do not implement snapshot-based incremental scanning in v1.** The native `IncrementalAppendScanBuilder` is unreleased, and even once available would not express deletes/overwrites, making it insufficient for correct upsert+delete sync on its own. Revisit once both the incremental append scan ships in a release **and** the changelog-scan issue (#1636) lands upstream, or once a documented pattern emerges for combining incremental-append with explicit delete tracking.
3. **Incremental sync for v1 reuses the existing column-watermark model** (`delta.updated_at_column`, identical to every other connector in this repo): each run performs a full `table.scan()` filtered client-side (or via `with_filter(...)` pushdown where the predicate maps to an Iceberg expression) to rows newer than the stored watermark, with soft-deletes handled via the existing `deleted_flag_column`/`deleted_flag_value` convention. This sacrifices Iceberg-native snapshot efficiency for v1 but matches proven, already-shipped repo semantics and avoids coupling to unreleased upstream APIs.
4. **Catalog support for v1**: REST (`iceberg-catalog-rest`) and Glue (`iceberg-catalog-glue`) as the two most common managed/open catalogs; SQL catalog (`iceberg-catalog-sql`) documented as a lightweight/local option. Hive Metastore (`iceberg-catalog-hms`) deferred as fast-follow since it requires a running HMS service to validate. No Hadoop/filesystem-only catalog type (doesn't exist as a dedicated crate).
5. **Storage backend**: use `iceberg-storage-opendal`'s `OpenDalResolvingStorageFactory` directly; no custom object-store client code needed. This also simplifies the shared `common/arrow-to-falkordb-bridge` crate planned for use by both `Parquet-to-FalkorDB` and `Iceberg-to-FalkorDB` — it can standardize on OpenDAL for storage configuration (S3/GCS/Azure/local credentials) rather than the originally assumed `object_store` crate, since OpenDAL already covers the same backends and is Iceberg's own dependency.
6. **Dependency footprint**: pulls in `arrow-*` (`58.x`), `parquet` (`58.x`), `opendal` (`0.57.x`) and transitively `reqwest`/`rustls`/AWS SigV4 signing crates. No native (non-Rust) system dependencies were required on macOS in this spike (unlike, e.g., the Oracle Instant Client requirement for `Oracle-to-FalkorDB`). Final Linux/musl runner-image footprint should still be measured as part of packaging/release work.

## Consequences
- The initial `Iceberg-to-FalkorDB` implementation proceeds with the full-scan + column-watermark design, not snapshot-incremental, reducing implementation risk and unblocking work immediately rather than waiting on upstream PRs.
- The shared bridge crate (`common/arrow-to-falkordb-bridge`) should be scoped to (a) Arrow `RecordBatch` → `LogicalRow` (JSON) conversion and (b) a thin OpenDAL configuration helper, rather than wrapping the `object_store` crate.
- A fast-follow item is tracked: revisit native Iceberg incremental/changelog scanning once apache/iceberg-rust ships both incremental append scan and changelog scan in a released version, which could replace the column-watermark approach with a more correct, more efficient snapshot-based design.
